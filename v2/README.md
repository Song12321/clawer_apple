# 并行下单 v2（多账号）

请求优化前先看 [必要请求链路](必要请求链路.md)：记录当前保留基线、各步作用、线上证据及省略请求的验证边界。

一个账号 = 一份配置 + 一个独立的浏览器资料目录 + 一个独立的调试端口 + 一个常驻 Chrome 会话。
`session.py` 和 `main.py` 共用 `RUN["参与账号"]`；`main.py` 为选中的每个账号启动一个工作线程；每个线程独立创建浏览器连接和 requests 会话。账号之间并行，同一账号的请求串行。缺货或失败不阻塞其他账号，每次运行每个账号成功一单即停止。

## 配置

`config.py` 分成两部分：

- `RUN`（运行级）：`参与账号`、`允许访客结账`、`使用抓包代理`、`缺货轮询间隔秒`、`结果文件`。
- `ACCOUNTS`（账号级）：账号名、资料目录、调试端口、商品与选配、门店、联系人、发票/支付。

账号级必填项由 `main.check_accounts` 在联网前校验：缺字段、重复账号名、重复资料目录、重复调试端口、数量不为 1、非支付宝/个人电子发票、证件后四位不足四个字符、端口非法，都会直接停止。

新增账号：复制 `ACCOUNTS` 里的那份，至少改四项——`账号`、`资料目录`、`调试端口`、商品与门店配置。资料目录建议写成 `str(BASE_DIR / "profiles" / "账号名")`。

## 运行顺序

在项目目录启动准备阶段：

```powershell
.venv/Scripts/python.exe v2/session.py
```

在 `config.py` 的 `RUN` 中设置 `"参与账号": "all"`（默认全部），或 `"参与账号": ["a138"]`，或 `"参与账号": ["a178", "a138"]`。两个脚本启动时读取同一配置并打印本次账号范围；session 仅为选中账号准备会话和显示心跳，main 仅为选中账号启动任务。无需交互输入；未知账号、空列表或重复选择直接报错。修改后需重启相应脚本生效，不会自动关闭未选账号已有的浏览器。

脚本启动或连接各账号浏览器，先校验购物袋：空袋加购；只有配置的同一件商品且数量一致则复用；其他情况停止，不自动清空或修改已有商品。随后通过当次模型发起结账，将该流程生成的 URL 和 Cookie 交给浏览器。准备阶段会加购并创建结账上下文，但不提交订单。

在对应窗口完成安全结账登录及双重认证，停在配送／自提（Fulfillment）页面，不要手动继续提交。已有结账或安全登录页面会被保留，不重新发起结账。main.py 检测到结账上下文缺失或明确过期时，会复用已有账号登录态自动准备一次。

首次完成认证后，保持浏览器窗口打开，另开终端：

```powershell
.venv/Scripts/python.exe v2/main.py
```

主流程预检浏览器及现有页面模型，并用一次结账 GET 验证 requests 会话仍可访问服务端；后续使用这次 GET 返回的最新 Fulfillment 模型。通过后读取商品选配与购物袋，校验 SKU、单件数量及金额，再接续 Fulfillment；有效会话直接接续；只有业务流程开始前发现上下文缺失或明确过期时，才重新准备一次购物袋结账。切换自提后直接按最新模型执行 select，提交配置中的固定门店，省略 search（21:34 已完成一次真实有货创单）。确认服务端选中的门店、商品及金额与配置一致，再使用选店响应声明的动作进入联系人页；缺少必需字段时明确停止，不退回旧模型。启动后不要手动操作窗口。

心跳只读现有页面，不发固定 secure 主机探针。它反映页面模型，不保证服务端会话一直有效；实际执行时重新验证；明确过期则自动准备一次，网络或模型错误直接停止，不视为登录过期。账户菜单、账户页可访问、履约查询成功均不作为结账认证完成的依据。

结果由主线程逐条写入，避免并发写混行；账号一旦成功就退出，不重新入队。账号失败不终止其他任务，所有任务结束后存在失败则非零退出。结果追加到 `RUN["结果文件"]`。主流程可能创建真实待支付订单，不执行付款，不自动重试创单。

## 认证与交接边界

`main.py` 必须取得有效 Fulfillment 页面；下单前允许自动准备一次，实际进入安全登录页时输出 `[需要人工认证]` 并保留浏览器窗口。请完成认证后重新运行 main.py。即使配置 `允许访客结账=True`，也不转访客结账。底层访客函数保留供既有离线回放使用。主流程不等待人工登录或输入短信，服务端要求额外短信认证时停止。

Cookie 只在准备交给浏览器、执行交给 Python 时同步，后续不是双向实时同步。交接包含实际结账主机的 Cookie，不仅是商品页域名；URL、令牌不写入额外状态文件。

Fulfillment 的已知 HAR 商品项没有数量字段，因此数量先通过购物袋校验为 1，并核对结账商品单价与该项总价、结账总额与购物袋总额；缺字段或不一致立即停止。

## 抓包代理

`RUN["使用抓包代理"]` 默认 `False`：Python 请求直连。实测让请求经 Reqable（127.0.0.1:9000）会**间歇性卡住**（同一商品页直连 0.08s、经代理 12s 超时，多次复现），而且浏览器导航经该代理会卡在 `about:blank` 直到超时。需要抓包时把它改成 `True`，并确认 Reqable 状态正常。浏览器始终直连，不受该开关影响。

## 常见问题

- “没有检测到常驻会话”：先运行 `session.py`。
- “结账未就绪”：在准备窗口完成安全结账认证，停在配送／自提页面；普通账户登录不够。
- “需要唯一的已准备结账页面”：每个账号保留一个目标结账标签页。
- `[需要人工认证]`：在对应账号窗口完成认证后重新运行。明确结账过期会在提交前自动准备一次；不要直接拼接 `/shop/signIn` 或复用历史 ssi。
- `session.py` 的 Ctrl+C 保留浏览器。`main.py` 的 Ctrl+C 立即唤醒缺货等待，当前请求返回后停止后续动作；若创单已提交，则继续查询并保存该次结果，不重新提交。

## 缺货等待与并行边界

`RUN["缺货轮询间隔秒"] = 15` 表示收到缺货响应后再等 15 秒重试 select，不包含请求耗时。切换自提时默认地区提示无货，仍向 select 提交配置门店及地区，不先搜索。目标门店明确不可取货或履约模型返回已确认的“你所在的地区无货可取。请尝试重新搜索。”时等待重试；进入联系人前出现同一缺货状态也回到 select。

其他业务错误、门店不在结果中、网络错误和 HTTP 541 均停止该账号，不按缺货重试。强制认证输出 `[需要人工认证]`。库存等待期间使用同一账号会话，账号间不共享 Cookie、模型或 Playwright 对象。启动时不再因某个账号浏览器不可用而阻止其他账号执行，但重复资料目录/端口等配置错误仍整体停止。

每个账号每次运行最多发送一次创单请求；结果不明也停止。成功记录立即落盘，无须等缺货账号结束。重新启动是一次新运行，不根据历史成功记录自动过滤账号；已有订单结果页仍会阻止重复提交。不要同时启动多个 main.py 操作同一账号。
