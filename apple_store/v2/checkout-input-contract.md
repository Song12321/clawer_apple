# 下单入参来源与实现缺口

目标：Python 发出商城业务请求，完成指定商品加购、访客结账、联系人填写、支付宝选择、提交订单并取得新订单号。本文是实现前的契约清单，不代表已经完成或验证交易。依据同目录 har-evidence.md 所标识的 HAR；不使用历史 Cookie、令牌或个人信息作为新订单配置。

“只指定产品”指其他用户资料已预配置，不代表下单不需要联系人、门店或当次验证码。纯 Python、无需浏览器、无需人工验证码是额外尚未证实的能力。

## 当前文件状态（2026-09-20 重新读取）

`apple_order.py` 的 main 目前止于加购并核验购物袋；存在 checkout_bag、query_order、read_order 辅助函数，但主入口未连接结账。当前文件没有 checkout_order、guest_form、verification_token、check_review。其来源变化未经调查，不恢复或覆盖现有文件。此前 checkout-implementation.md 中“主入口已连接全链路”的描述属于历史状态，不应作为当前能力依据。

## 收敛后的执行顺序

1. 先把剩余可从 HAR 直接确认的字段补齐：加购参数、身份组件 query、全程请求头来源。以字段值匹配和具体路径交付，不扩展为通用浏览器指纹研究。
2. deviceID 只围绕“能否取得当次合法值”做有限验证；暂不要求完整移植算法。若需要浏览器运行，明确它与“商城业务请求全部由 requests 发送”的边界，不宣称纯 Python 无浏览器。
3. 实施时先补已确认契约：POST+args 导航、证件后四位、联系人验证和本样本支付字段。当前仅整理清单，不擅自恢复已不在文件中的历史实现。
4. 用新会话逐阶段验收；541 不得靠忽略错误、重放旧凭据或无限重建会话掩盖。真实创单前核对精确目标和授权，响应不明时不重复提交。

验收分三层：历史链路可解释；新会话阶段请求通过；新订单创建并返回订单号。前两层不能代替第三层。短信参与和有效会话仍是当前全自动目标的关键约束。
