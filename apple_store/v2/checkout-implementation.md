# requests 访客结账实现

`apple_order.py` 主入口已连接：加购、购物袋核验、访客入口、指定门店自提、联系人验证及填写、支付宝、Review 核验、提交订单、状态查询和返回订单号。`checkout_order()` 返回含 `订单号`、`订单链接` 的字典，`main()` 返回各会话结果列表；终端只打印订单号，不打印含会话信息的查询链接。

所有商城业务提交由同一个 `requests.Session` 执行。Chrome 用于初始化官网会话、生成访客 deviceID，以及运行官网联系人验证组件。访客表单在浏览器发出前被截获并取消，再交给 requests。联系人组件通过 `AppleID.service.verify.init` 的 `onComplete` 返回当次 token，随后由 requests 提交 `submitVerificationToken`。需要验证码时，在该 Chrome 窗口完成验证；不是无人值守验证码方案。

配置沿用脚本中的 `CONFIG` 和 `SESSION_CONFIGS`，没有命令行配置参数。当前实现限定单件商品、指定门店自提、个人电子发票和支付宝。门店不在当次列表或不可取货时停止，不自动换店。执行主脚本会在各项核验通过后创建待支付订单，不执行付款。

最终动作依据官网 `checkout.js` 的 POST 表单序列化逻辑和 Review 的 `placeOrder` 按钮绑定；只提交该模块子树，目前为空体。若模块范围或提交字段变化则停止。验证响应为局部模型时，仅更新原联系人模型的最新请求头，不猜测通用模型合并规则。

## 验证及边界（2026-09-19）

- 离线回归覆盖完整 requests 调用顺序、当次验证令牌提交、请求头版本更新、支付宝直接进入 Review 的响应、订单号提取，以及库存不足、验证失败、订单内容变化、新增提交字段、提交超时及结果未知时停止且不重复创单。
- 已用本机历史响应只读核对 Review 字段结构、联系人阶段门店摘要与选中门店的一致性、验证响应的请求头；未重放历史凭据。
- 在线验证到加购、购物袋结账和访客页面。发现并修正 React 实际按钮 ID 与模型 `b.id` 不一致的问题。修正后的下一次在线验证在初始化履约查询遇到 HTTP 541，未加购，停止测试。
- 因此，访客提交、当次联系人验证、支付选择、最终创单和取得真实订单号尚未通过端到端在线验证。本次未创建真实订单，不能将离线成功当作实际下单成功。
- 状态查询沿用已确认的一次 `checkStatus` 请求；非结果页响应会明确停止，不报告成功，也不再次提交订单。

本地测试：`venv/Scripts/python.exe -m unittest discover -s apple_store -p "test_*.py"`。

## 541 专项诊断（同日）

541 可在浏览器页面原生履约请求中出现，发生在 requests 会话交接之前；验证接口 HTTP 200 和 `shldDone` 事件均不足以证明履约可用。同一代码也出现过浏览器与 requests 均 200 的初始化结果，故不能将偶然成功认定为根因已消除。普通临时 Chrome 窗口对照同样出现 541；商品页面 GET 返回 200，客户端与服务器时钟相差不足 1 秒。

已移除原生履约请求之后的重复浏览器 fetch，改为直接检查原生响应的 HTTP、业务状态及错误消息。原生 541 时不再探测或交接 requests。改动后在线检查仍为原生 541，**尚未解决服务端拒绝的根因**。需要与用户日常浏览器手动访问结果对照；不自动重建会话或重试业务请求。
